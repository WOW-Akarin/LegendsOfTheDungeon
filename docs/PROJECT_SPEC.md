# LegendsOfTheDungeon 项目设计与开发规范

> 文档版本：1.1（优化版）  
> 修订日期：2026-11-16  
> 适用范围：LegendsOfTheDungeon 通用 C# 游戏服务器核心  
> 配套文档：[架构设计](ARCHITECTURE.md)、[开发与验收路线图](DEVELOPMENT_ROADMAP.md)  
> 说明：本版是文档设计基线，不代表代码已经实现或通过验收。项目实际状态以仓库、测试证据和进度记录为准。

## 1. 目标、范围与交付边界

研究 AzerothCore（以下简称 AC）中可泛化的服务器机制，重新设计为模块化、可测试、可扩展的 C# / .NET 10 核心。保留模块化单体、World Actor、Ports & Adapters 的方向。

必须覆盖的能力域：Kernel、Platform、静态数据、World Runtime、实体能力、移动、战斗、Ability/Effect/Status、Items/Inventory/Loot、Progression/Objectives、AI、交互与在线状态、通用场景、脚本扩展、安全管理、持久化、模拟与工程工具。

这些是整体交付范围，不要求在每个模块的首个任务中穷尽所有策略、数据源和算法。各阶段应先交付真实可运行的最小实现，再按路线图补齐。能力不可用时必须显式返回“不支持/未配置”，不得用固定成功结果冒充实现。

明确排除：WoW 客户端兼容、3.3.5a/Build 12340、WoW Opcode/数据包、SRP6/HeaderCrypt、DBC/DB2 强制兼容、AC 数据库逐表兼容、具体职业/种族/天赋/Glyph、具体副本/Boss、LFG/PvP/Warden，以及完整 WoW Guild/Mail/Auction/Chat 玩法。通用传输帧、认证接口、可配置装备槽和通用场景仍属于核心能力。

准入问题：移除 WoW 上下文后是否成立？是否有当前真实使用场景？能否通过替换数据或策略用于其他游戏？不满足时不进入 Core。

## 3. 关键架构约束

以下约束的技术定义以架构文档为准：

1. 每份可变状态只有一个领域所有者；WorldExecutor 是世界状态的唯一合法写入上下文，两者不是同一概念。
2. 同一 World 串行执行，多 World 可由有限运行时工作线程调度。
3. 外部输入、DB 回执和离线计算结果经有界 Mailbox 进入世界；不得持有可变实体引用回写。
4. 跨模块使用明确的 Command、Query、Domain Event 或 Runtime Capability；禁止访问对方 Internal/Infrastructure。
5. Domain 不依赖 DB Driver、Transport、Host；具体 Adapter 由组合根装配。
6. 静态定义、运行时实例、持久化记录、只读快照分别建模。
7. 不建立万能 Manager、Repository、Service Locator 或 Common/Utils。名称扫描只能辅助，职责审查才判断是否形成中心对象。
8. 高频同步操作保留明确调用顺序；事件发布发生在成功提交之后。
9. 持久化确认、幂等、崩溃恢复和跨聚合操作必须有明确语义，不能仅写“支持事务”。
10. 可确定性测试必须覆盖输入排序、时间、随机、静态数据版本和外部结果，而非只固定一个 Seed。

## 4. 工程与公共契约

### 4.1 工程基线

- 使用 .NET 10；在 `global.json` 固定实际安装并验证过的 SDK 版本及 roll-forward 策略，不使用 `latest` 作为基线。
- 集中管理依赖版本、启用 Nullable 和分析器，记录目标操作系统、架构、数据库及测试环境版本。
- 仓库建立后提供统一验证入口。命令必须以实际项目路径为准，文档示例不等于命令已执行。
- 从干净环境验证 restore/build/test；锁文件策略、包源和缓存失效方式纳入 CI。
- 性能、数据库和长稳任务可以分层运行，但必需 Gate 未通过时不得声称阶段通过。

### 4.2 Contract 变更记录

每次新增或修改公共契约，至少记录：

```text
契约 ID / 版本：
提供模块 / 状态所有者：
真实调用场景 / 调用方：
读写类型 / 频率 / 单位：
同步或异步 / 合法执行上下文：
输入、输出、错误码：
取消、超时、重复、乱序语义：
是否涉及持久化 / 成功确认点：
兼容与迁移方式：
相关测试 / ADR / AC 参考：
```

无真实调用方时不要预建大接口。查询返回不可变 DTO 或快照；`IReadOnlyList<T>` 不代表其元素和底层集合不可变。写 Capability 不向脚本、网络或后台任务泄漏。

破坏性变更同时更新实现、调用方、序列化版本和测试；无法一次迁移时，写清兼容窗口、弃用版本与删除条件。

## 5. 中文注释与文档

### 5.1 代码注释

手写公共类型和公共成员使用中文 XML 注释。按适用性说明职责、参数及单位、返回值、错误/异常、取消、状态所有者和执行上下文；纯值对象无需重复无关的 DB/World 说明。所有非显然逻辑应解释原因和不变量，重点包括状态机、Tick 顺序、事务、补偿、并发、时间、随机、缓存失效、复杂公式及去重。

```csharp
/// <summary>
/// 在实体所属世界中申请位置变更。
/// 成功时由重定位协调操作同时提交 Transform 与空间索引更新；
/// 校验失败时二者均不改变。外部调用方应通过命令入口请求。
/// </summary>
/// <param name="entityId">实体标识，必须属于当前世界。</param>
/// <param name="position">位置，采用项目约定的世界单位。</param>
/// <returns>提交结果；失败包含实体不存在、位置非法等原因。</returns>
```

自动生成代码、第三方源码和测试夹具不要求人工逐成员补注释；在生成规则或来源记录中说明，不得借此豁免手写 API。编译器/分析器检查 XML 缺失；人工检查中文质量、并发和语义。不能用“出现中文字符”判断注释合格。

引用 AC 的复杂机制通过稳定研究记录链接到 Commit/File/Function、采用语义和差异；无需每个辅助方法重复大段来源。

### 5.2 中文文档

手写说明文档使用中文，类型名、命令、标准术语和第三方原文可保留英文。重要决定与实现同步更新；废弃设计标明替代文档，禁止保留两份互相矛盾的“现行规则”。

Markdown 代码围栏应正确配对，嵌套示例使用更长的外层围栏。相对链接采用仓库内真实路径，不写开发机器绝对路径。

## 6. AC 研究与来源管理

`docs/UPSTREAM.md` 至少记录仓库 URL、完整 Commit SHA、研究日期、使用的源码路径、获取方式及基线更新历史。本文未提供 AC 实际 Commit，不得自行填造。

每个研究主题在 `docs/research/azerothcore/` 记录：

```text
主题 / 上游基线 / 文件 / 函数：
原始职责 / 前置条件 / 单位：
可泛化机制 / 明确排除的 WoW 部分：
Legends 映射 / 已知差异及原因：
输入向量 / 预期结果 / 推导或生成方法：
参考可信度：源码分析 / 提取测试向量 / 实际运行对照
对应契约 / 测试路径：
来源文件许可 / 复用方式 / 归属记录：
```

禁止按 C++ 类名机械翻译。AC 是参考材料，不是所有设计的唯一正确答案。记录参考行为与本项目策略的差异；不能为了“对齐 AC”引入 WoW 专用依赖。

复制、改写或分发上游代码、数据、测试向量之前核对实际来源许可与归属要求；不能假定改为 C# 就免除原有义务。仅研究思想与直接复用代码分别记录，具体结论以实际文件和复用方式为准。

## 7. 开发、审查与验收流程

读取当前规范与恢复记录 → 确认阶段入口、状态所有者和契约 → 更新任务状态 → 必要研究/设计 → 实现 → 运行适用检查 → 自审 → 更新文档及证据 → REVIEW → ACCEPTED。

审查覆盖四个视角：功能正确性、契约与架构、失败与恢复、证据可复现性。同一任务中的实现检查和最终验收应分成两个明确步骤；自审记录结论与未解决项。不得以“已编译”替代完整验收。

每个任务应有明确结果、修改范围、依赖、完成条件。变更公共契约之前检查所有调用方；实施大规模重构前记录当前基线、工作区状态和恢复入口。不得覆盖已有未提交工作。

### 7.1 测试适用性

| 变更 | 必需证据 |
|---|---|
| 纯文档/规划 | 链接、围栏、术语、跨文档一致性和人工审阅；已有文档检查按需执行 |
| 纯算法/值对象 | 确定性单测、边界和非法输入；必要时性质测试 |
| 跨模块契约 | 提供方与真实调用方契约测试、架构检查 |
| 世界运行时 | 上下文违规负例、并发、生命周期、队列过载、回放 |
| 持久化/经济状态 | 真实选定数据库集成、事务与崩溃故障注入、重复请求 |
| 高频路径 | 固定负载的性能及分配基线 |
| 脚本/外部入口 | 授权、输入限制、异常、预算和能力边界 |

每个验收项标记 PASS/FAIL/N/A/NOT_RUN。N/A 必须说明不适用原因；NOT_RUN 不是通过；必需证据未执行不能 ACCEPTED。P00/P01 尚无 Solution 时不强求执行 dotnet 命令。

禁止为通过验收删除、Skip 或无理由弱化测试。行为因正式需求变更时可以同步更新测试，但需记录旧行为、新行为和变更依据。可控逻辑时间测试不用真实 Sleep；真实网络、时延和长稳测试允许有界等待和明确超时。统计分布测试使用固定输入及有依据的容差，避免不稳定断言。

### 7.2 证据包

阶段证据放在 `docs/progress/Pxx.md`，大报告放在 CI artifact 或约定产物目录并提供持久链接。记录：代码 Commit 或工作区差异摘要、文档版本、环境、命令、结果、原始报告、数据/Seed、失败案例、已知限制、自审结论。

没有执行的命令不得记为成功；模拟实现不算真实数据库/网络集成证据；源码推导不算实际 AC 运行对照。

## 8. 阶段状态与完成度

```text
NOT_STARTED → IN_PROGRESS → REVIEW → ACCEPTED
                   ↕           │
                BLOCKED        └→ IN_PROGRESS（退回修正）
```

BLOCKED 必须保存阻塞前状态和恢复入口，解除后回到 IN_PROGRESS 或 REVIEW。未完成阶段只有在记录范围依据、影响及重排后才能 DEFERRED；重新启动时回到 NOT_STARTED 或 IN_PROGRESS。DEFERRED 不是完成。已验收阶段受新变更影响时创建回归任务，必要时重新打开为 IN_PROGRESS，并保留旧验收证据。

阶段状态和完成度是不同维度：A=结构存在，B=模块功能，C=真实依赖集成；D=适用机制完成 AC 参考验证。D 仅在存在参考范围时要求，不意味着高于所有其他质量维度。性能、安全和运维仍须单独验证。每阶段目标等级由路线图规定。

BLOCKED 模板：阻塞原因、缺失契约/数据/决定、影响阶段、可继续的工作、下一安全动作、解除条件。禁止用访问 Internal、固定成功结果或临时万能服务绕过阻塞。

## 9. CONTEXT 与 PROGRESS 恢复制度

### 9.1 当前摘要

`docs/CONTEXT.md` 只保留当前范围、架构不变量、当前里程碑、已具备能力、当前任务/下一步、阻塞、关键契约/所有权入口、Accepted ADR、AC 基线、技术债和重要文件链接。标注更新时间与对应代码基线。

阶段验收、重大决策、方向切换、摘要失真和工作结束时更新。历史移入 `docs/progress/`，保留决策原因和入口，不复制聊天全文。摘要更新属于文件维护，不保证任何对话系统会自动压缩上下文。

## 10. 规范和设计变更

| 类别 | 内容 | 必须记录 |
|---|---|---|
| S0 | 说明、示例、纠错，不改变行为 | 变更原因和位置 |
| S1 | 新增质量约束，不改变范围和核心模型 | 影响、成本、适用时间、存量迁移方式 |
| S2 | 范围、核心模型、所有权或验收标准变化 | ADR、替代方案、迁移和相关基线更新 |

不得以“自优化”为由无限扩张 Gate 或静默降低标准。范围变化需要有明确的需求依据；现有用户要求已经覆盖的事项无需重复征求确认。新增架构决定须说明成本与完成条件，避免只写禁令。

架构审查分级：A0=内部实现；A1=公共契约；A2=跨模块依赖/所有权；A3=核心执行或一致性模型。A1 更新契约与调用方测试；A2/A3 更新架构、ADR 和回归证据。S 类表示规范变更，A 类表示实现影响，二者不可混用。
